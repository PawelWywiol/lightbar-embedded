# Frame repeat

Each frame gets a repeat count 0-255 set in the web scheme editor and honored by firmware. Example scanner: frame A with pixel shift +1 repeated N times, frame B with pixel shift -1 repeated N times.

## Decisions

- Repeat means extra plays: N plays the frame N+1 times; 0 plays once.
- Every frame is encoded as `frm3`. Types `fram` and `frm2` are removed from firmware and web.
- Existing data is migrated: D1 rows re-encoded by migration `0008_frame_repeat.sql`, embedded presets re-exported with `make presets`, test boards updated with `uploadfs`.
- Editor control: fourth select 0-255, 0 labeled as no repeat, with tooltip.
- Stretch resize keeps repeat unchanged (pixel shift already scales with length).

## Binary format

Chunk type `frm3` = `0x66726d33`. Payload:

| Byte | Field |
| --- | --- |
| 0 | flags (type, shuffle, hue shift) |
| 1 | pixel shift, int8 |
| 2 | repeat, uint8 |
| 3 | tempo |
| 4.. | colors |

## Playback

- A step stays on the same frame while repeats remain, else moves to the next frame and resets the repeat counter.
- Every step adds the frame hue shift and pixel shift and lasts the frame tempo.
- Fade frames interpolate to the next step: the same frame with offsets added again, or the next frame after the last repeat.

## Firmware

- `CONNECTION_REQUEST_FRAME_INFO` becomes `frm3`; `CONNECTION_REQUEST_FRAME_V2_INFO` and the v1/v2 header sizes go away; single header size 4.
- `frame_data_t.repeat`; `lights_data_t.current_frame_repeat`.
- `next_frame_index()` returns the current index while repeats remain; used by the step in `resolve_current_light_schema_frame` and by `resolve_next_strip_colors`.
- Frames are not duplicated in RAM.

## Web

- `LightsFrame.repeat: number`; `createFrame` sets 0; `updateRow` accepts `repeat`.
- `CONNECTION_REQUEST_TYPE.frame` = `0x66_72_6d_33`; `CONNECTION_REQUEST_LEGACY_FRAME_TYPE` removed; encoder and decoder use the 4-byte header.
- Editor row: repeat select next to tempo, hue shift, pixel shift; messages in all locales.
- Preview, scheme period and offset helpers run on frames expanded by `repeat + 1`; the changed-frame index is mapped to its position in the expanded list.
- Migration generated by a one-off script outside the repo: read all rows from remote D1, re-encode to `frm3`, emit `UPDATE` statements. Only the SQL file is committed. It is applied automatically on push to `main`.

## Rollout

1. Web PR: code, tests, migration. Merge applies the migration and deploys.
2. Firmware PR: code, presets re-exported after web deploy.
3. `uploadfs` and firmware upload on test boards.

## Testing

- Web: unit tests for encoder, decoder, frame expansion, editor row, preview.
- Firmware: build all environments; hardware test on C3 with a scanner scheme (two frames, shift ±1, N repeats).

## Open questions

- Compacting presets made of duplicated frames (e.g. comet) into repeats: separate task.
- Rows changed between generating the migration and merging the web PR keep the old format; generate the migration right before merge.
